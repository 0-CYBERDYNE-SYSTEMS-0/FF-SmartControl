01 · The model class

A new kind of model, built for software — not for talking to humans

Named after Kahneman’s Thinking, Fast and Slow: LLMs are deliberate “System Two” text generators. System One models are the fast, intuitive layer — trained with RLCD (Reinforcement Learning for Calibrated Decisions) to answer many typed questions in parallel, in one query, with epistemically honest probabilities attached.

🚫💬
No strings

It cannot produce prose — so it cannot produce a hallucinated sentence, a malformed JSON blob, or a refusal disguised as an answer. Outputs are constrained to types you defined.

⚡
Parallel sampling

All answers are emitted in one query, not one token at a time. No autoregressive bottleneck — that’s where the 40–200× speedup comes from.

🎯
Calibrated

Every answer carries a probability, and the probability means something: higher confidence correlates with higher accuracy. This unlocks probability-thresholded automation.

🧩
Composable

Designed as a “smart if-statement” inside ordinary code — classify, route, score, extract, branch — while surrounding code keeps state, policy, and side effects.

System Two — what we use today

LLMs (Ollama qwen3.5:2b locally, MiniMax/GPT-class in the cloud) generate a string and we hope it contains a well-formed decision. Flexible, great at explanation — slow, costly, occasionally off the rails.

System One — what Jev adds

Bounded semantic judgment as a library call. Code owns state, arithmetic, policy, and actuation; the model answers “what should we do?” with typed values and honest odds, in milliseconds.

03 · Why it fits this codebase

Our decision loop already bends itself into an LLM’s shape.
Jev just… is that shape.

runDecisionCycle() (src/agent/decision-loop.ts) asks the LLM for one JSON object and then spends real engineering defending itself from the format. Each row below is live code we maintain today.

Today · defensive parsing

extractDecisionJson() — ~50 lines of balanced-brace, string-aware scanning, because reasoning models wrap JSON in prose and markdown fences. A mis-parse silently turns a valid turn_on into a no-op.

→
With Jev

The response is the typed object. The function deletes itself. No fences, no scan, no silent degradation.

Today · schema triage

Zod DecisionPayloadSchema downgrades out-of-contract payloads (unknown verb, non-numeric confidence, junk tool_calls) to a safe noop that smuggles the raw text into the audit trail.

→
With Jev

Type errors are mathematically impossible (TypeSafe’s claim — schema match is guaranteed, falsifiable by a single counter-example). Zod stays as a cheap tripwire, not a way of life.

Today · hallucinated device guard

An LLM inventing device_id: "Pump A" (human label, not id) would throw an FK error and kill the cycle — so we null it and force a noop.

→
With Jev

target_device is an enum built from the live registry. A farm’s device count sits comfortably under Jev’s 255-choice ceiling. Inventing an id isn’t possible.

Today · decorative confidence

LLM confidence is prompted-for and overconfident and inconsistent (TypeSafe’s critique, and our audit logs agree) — so it’s logged, never acted on.

→
With Jev

Calibrated p becomes a real control input: gate AUTONOMOUS actuation on it, route mid-band decisions to SUGGEST, watch calibration drift in the audit log.

Today · latency-bound beats

Heartbeat decisions wait seconds-to-minutes on the model, and the sim’s efficacy runs pay for every reasoning token.

→
With Jev

Sub-second decisions make tighter loops honest: tick triage on every beat, actuation without the coffee break, and cheap shadow-mode evals at scale.

04 · Where it slots in

Jev proposes. The verifier still disposes.

The Safety Spine is our moat and it does not move. Jev replaces the decision proposer only — everything amber is new surface; everything red is exactly the code that ships today.

new Jev surface stays on LLM safety spine — untouched existing infra
① Tick triage

Today every heartbeat pays for a full LLM call. With triage at ~$0, the expensive path runs only when something looks actionable — and noop spam thins out of the decision log.

② Intent router

runFarmPalTurn classifies each message (status / diagnostic / reflection / control / emergency_stop) before routing. Pure classification is the canonical Jev task — and calibrated p on emergency_stop is exactly the alarm you want honest.

④ Second opinion

TypeSafe’s “verify everything” use case, aimed inward: score the Generator’s proposals in the turn path before the deterministic verifier — a cheap pre-filter, never a bypass.

05 · What the call looks like

Same state we prompt with today — typed answers out

One parallel query replaces the “respond ONLY with a valid JSON object” incantation. Shape is illustrative, based on TypeSafe’s published query format (state paragraph + typed questions); the exact API lands with early access.

POST /v1/decide — one query, all answers in parallel
{
  "state": "tents: A(t=27.8C rh=41% soil=18% co2=890) B(t=24.1 rh=55% soil=44%).
          devices: pump_01=off fan_01=off light_01=off heater_01=off.
          recent: fan_01 turned_on 14m ago (heat advisory). e_stop=clear mode=AUTONOMOUS",
  "questions": {
    "action":        "enum:turn_on|turn_off|adjust|alert|noop",
    "target_device": "enum:pump_01|fan_01|light_01|heater_01",
    "act_now":       "bool",
    "urgency":       "int:1-5"
  }
}

// → 200 OK in ~120ms — no prose, no fences, no parse
{
  "action":        { "value": "turn_on",  "p": 0.97 },
  "target_device": { "value": "pump_01", "p": 0.96 },
  "act_now":       { "value": true,      "p": 0.94 },
  "urgency":       { "value": 4,        "p": 0.91 }
}

The p column is the upgrade no prompt-engineering session gets us: honest, consistent odds we can gate hardware on — and the audit trail already has a column waiting for the model name.

06 · The new dial

Calibrated confidence turns mode-switching into a spectrum

Today autonomy is binary per mode: OBSERVE_ONLY (factory default), SUGGEST, ASSISTED, AUTONOMOUS — and autonomy stays an explicit operator action. Inside AUTONOMOUS, calibrated p adds a per-decision gate. Drag it:

log only · < 0.80
suggest · 0.80 – 0.95
auto-execute · ≥ 0.95

Below the gate nothing regresses to chaos: mid-band decisions land in the SUGGEST queue exactly like ASSISTED mode does today, and the verifier + E-stop still own the final word on everything. Calibration drift is observable from the audit log — if p stops meaning accuracy, we tighten the gate.

07 · Integration sketch

A new module beside llm.ts — not a replacement of it

Provider order for decisions becomes jev → ollama → cloud. No key, no network, no change: the legacy path remains the factory default and the fallback.

src/agent/jev.ts — new
// Sits beside llm.ts. Returns null on any miss → caller falls back. Zero behavior change.
export async function decideWithJev(input: {
  state: string;                          // registry + sensor snapshot (same data we prompt today)
  questions: Record<string, string>;      // typed questions incl. device enum from halRegistry
}): Promise<Record<string, { value: unknown; p: number }> | null> {
  const key = process.env.JEV_API_KEY;
  if (!key) return null;
  try {
    const res = await fetch(`${process.env.JEV_BASE_URL}/v1/decide`, {
      method: 'POST',
      headers: { Authorization: `Bearer ${key}`, 'Content-Type': 'application/json' },
      body: JSON.stringify(input),
      signal: AbortSignal.timeout(1_500),   // sub-second budget; a miss is a fallback, not a failure
    });
    if (!res.ok) return null;
    return await res.json();
  } catch { return null; }                // unavailable → LLM fallback or existing safety hold
}

08 · Division of labor

What moves, what stays, what never touches it

Moves to Jev

  • Heartbeat decision core in runDecisionCycle — action, device, urgency
  • Tick triage — “worth a full decision?” on every beat
  • Intent routing in runFarmPalTurn, incl. honest p on emergency_stop
  • Generator-proposal scoring — pre-verifier second opinion
  • Numeric-telemetry anomaly flags (threshold-adjacent judgment calls)

Stays on the LLM

  • Chat answers & operator Q&A — Jev cannot emit prose
  • Diagnostics narrative & reflector self-analysis
  • Camera vision — no image input yet (“not on images (yet…)”)
  • Audit reasoning text — templated from Jev fields; paired LLM call only when we actuate
  • Fallback lane — ollama-first when Jev is unreachable or key-less

Never touches Jev

  • Policy engine / safety verifier — rules stay deterministic
  • E-stop — hardware truth, no model in the path
  • Actuation chokepoint — verify → execute → re-verify
  • Audit trail — append-only, model-agnostic
  • OBSERVE_ONLY factory default — autonomy remains an operator action
09 · Honest constraints

What we’d be signing up for

Extraordinary claims got a whole section on TypeSafe’s blog. The ones that matter to a product shipped on an SD card:

Early access

Waitlist-gated. Not shippable in the $299/$449 product today; API shape may move. Build behind JEV_API_KEY and nothing breaks if it never opens.

Cloud-only, today

Service is currently West-Coast hosted. Our SD-card product is offline-capable by ethos, and sensor telemetry leaving the property cuts against the on-prem privacy pitch. Jev stays optional for connected installs; ollama remains the default brain.

No images yet

The camera path (describe_camera, ollama-first vision) is untouched — Jev’s demos run on structured state as text, explicitly “not on images (yet…)”.

Vendor-reported numbers

193×/444× come from TypeSafe’s own workflow evals against two named frontier models. Independent benchmarks don’t exist yet. Our Phase-0 sim eval is the receipt that counts.

“Can’t hallucinate” ≠ “always right”

The guarantee is type/schema, not correctness. A confident, well-typed wrong turn_on is still wrong — which is precisely why the verifier keeps the last word.

Business fit

A one-time license + recurring cloud inference = a COGS question. Until pricing matures: BYO-key option, never a bundled dependency — and if this ever moves the product direction, DIRECTION.md changes in the same PR.
